## 30 秒简答

虚拟滚动就是：**列表有一万条，DOM 只渲染屏幕附近那几十条。**

做法是：外面一个可滚动容器，里面用一个很高的占位元素把滚动条撑出来；真正的列表项绝对定位，根据 `scrollTop` 算出当前该显示哪一段，用 `transform` 放到正确位置。滚动时只更新这一小段节点，所以条目再多，DOM 数量也大致恒定。

## 2 分钟标准答（对方说「展开讲讲」）

数据层先给每项一个高度（固定值，或 `estimateSize` 的估计值），累加成一条「虚拟尺子」：每项有 `start / size / end`。

视口对应尺子上的区间 `[scrollTop, scrollTop + viewportHeight)`。在尺子上找到落在这个区间里的 `startIndex ~ endIndex`，再向外多渲染几行（overscan），防止快速滑动露白。

渲染层只输出这些项。容器高度等于总高度 `getTotalSize()`，每一项 `translateY(item.start)`。

如果高度会变（图片、折行、聊天气泡），项挂上之后再量真实高度，写回缓存，从这一项起重算后面的 `start`。视口上方的项变高了，还要把 `scrollTop` 补同样的差值，否则画面会跳。

一句话：**几何计算在 JS 里做，DOM 只负责当前窗口。**

## 可能的追问和回答

### 1. 固定高度怎么算可见范围？

`startIndex = floor(scrollTop / itemHeight)`  
`endIndex = ceil((scrollTop + viewportHeight) / itemHeight)`  
再 `± overscan`，clamp 到 `[0, count-1]`。

总高度就是 `count * itemHeight`。这是最容易手写的版本，面试现场可以在白板上写完。

### 2. 高度不固定呢？

不能再除法了。先用估计高度（或已测高度）做前缀和，得到每项的 `start`。找可见起点用二分：最后一个 `start <= scrollTop` 的下标；再从这里往后扫，直到 `end >= scrollTop + viewportHeight`。

复杂度大约是 `O(log n)` 找起点 + `O(可见条数)` 找终点，和列表总长度几乎无关。

### 3. 为什么用二分，不能直接扫？

一万条每次滚动都从头累加会卡。前缀和是单调递增的，二分合法。TanStack Virtual 单列路径甚至把 `start/size` 放进 `Float64Array`，二分时不创建对象，就是为了滚动帧里少分配、少走对象访问。

### 4. overscan 是干什么的？

可视区两端多渲染几项。滚动是连续的，若刚好渲染视口里那些，下一帧新项还没挂上就会闪白。overscan 用少量额外 DOM 换流畅度。太大则虚拟化收益下降，一般 1～5，看项高度和滚动速度。

### 5. 为什么动态高度会「跳」？怎么修？

你先按估计高度排了位置，用户已经停在某个 `scrollTop`。后面某项真实高度变了：

- 变化发生在**视口上方**：上面变高，下面整段被顶下去，但 `scrollTop` 没变，眼睛看到的内容就跳。
- 修法：`scrollTop += delta`（尺寸差）。这叫滚动补偿 / 锚点保持。
- 变化发生在**视口下方**：不用补，用户还没看到。
- **横跨视口、在底部往下长**（流式聊天气泡）：不要按整段 delta 去加 `scrollTop`，否则视口会被一点点拖走。只补偿「完全在视口上方」的项。

第一次从估计变成实测，只要该项顶在视口上方，通常就要补；再次测量则更保守。

### 6. 聊天列表：顶部插入历史、底部跟新消息，怎么做？

两套锚点：

- **看历史 / prepend**：记住当前屏幕上某条的 `key`，以及它和 `scrollTop` 的相对距离。数据插到前面、尺子重算后，用 `新 start + 旧距离` 写回 `scrollTop`，眼睛还停在同一条。
- **贴底 / append**：用户本来就在底部，来新消息就 `scrollToEnd`。有的库用 `anchorTo: 'end'` + `followOnAppend`。还要处理「尾部加一条、头部丢掉旧消息、count 不变」的滑动窗口，不能只看 `count++`。

### 7. `scrollToIndex` 在不定高下列不准怎么办？

目标像素依赖尚未测量的项，第一次 `scrollTo` 往往只是近似。滚过去的过程中新项被测到，总高度和目标都会变，所以要**对账**：记下目标 index，rAF 里根据最新尺子重算目标偏移，不够再滚；快到了从 smooth 改成 auto，避免终点一直漂。这就是「滚动对账 / reconcile」。

### 8. 和分页、和 `content-visibility` 的区别？

| 方案 | 本质 |
| --- | --- |
| 分页 / 无限加载 | 数据可以不全在内存，但已加载的通常都在 DOM 里 |
| `content-visibility: auto` | 浏览器跳过离屏绘制，节点还在 |
| 虚拟滚动 | **DOM 数量有上限**，未进入窗口的节点不存在 |

大数据表格、聊天、日志，虚拟滚动更合适。SEO、需要浏览器全文搜索、需要原生选中跨很多行，虚拟滚动会变痛。

### 9. 节点是销毁重建，还是回收复用？

两种都行。

- **销毁重建**（TanStack Virtual 默认）：可见集合变了就按 `key` 渲染新节点。实现简单，React/Vue 协调器很熟。
- **回收池**（旧版 react-window 一类）：固定 N 个节点，改文本和 `transform`。滚动极快、项很轻时少 GC，但和框架状态、动画、焦点更难搅在一起。

面试可以讲：先重建，量出来再考虑池化或直接改 DOM（有的库有 `directDomUpdates`，滚动时不触发 React 渲染，只改 `transform`）。

### 10. 为什么用 `transform` 而不是改 `top`？

`transform` 多走合成层，不轻易触发布局；`top` 会触发 layout。长列表滚动时 `translateY` 通常更稳。代价是会创建层叠上下文，里面的 `position: fixed` 可能不符合预期。也可以 `top`，看场景。

外层必须 `overflow: auto`，内层 sizer 给总高度，项 `position: absolute`。这三件套说不全，面试官会觉得没写过。

### 11. 横向、表格、瀑布流怎么虚？

- 横向：同一套算法，轴换成 `scrollLeft` / `width`。
- 表格：经常 **两个** 虚拟器，行一个、列一个。
- 瀑布流：`lanes > 1`，新项放到当前最短的那一列，不是二维网格。网格是行列索引；masonry 是一维列表 + 最短列。

### 12. 性能上还会卡在哪？

虚拟滚动解决的是 **DOM 数量**，不是：

- 每一项内部很重（大图、复杂图表、每项一个重型子树）
- 滚动回调里 setState 导致整树协调（应只在可见范围变化时渲染，或直接改 DOM）
- 同步 `offsetHeight` 读得多，强制 layout
- `key` 用 index，插入/重排后高度缓存错位——要用稳定 `getItemKey`
- overscan 过大、或错误地把所有项都 mount 了（只是藏起来）

### 13. 什么时候不要用虚拟滚动？

条数少（一两屏）、项高度差极大且很难估计、必须原生全文查找/打印、无障碍要求完整 DOM、SSR 要输出全部内容。这时虚拟化的复杂度和坑比收益大。

### 14. 无障碍怎么补？

屏幕阅读器看不到未渲染项。常见补法：容器上标总数和当前范围（`aria-rowcount` / `aria-setsize` / `aria-posinset`）、滚动时不要抢走焦点、程序化滚动后把焦点放到目标项。没有完美方案，要承认这一点。

### 15. 手写一个和用 TanStack Virtual / react-window 怎么选？

固定高度、需求简单：现场手写 40 行就够，也最能证明理解。

不定高、聊天、平滑滚动、iOS 惯性里不能乱写 `scrollTop`、prepend 锚点：自己写这些边角会爆。用成熟库，但要能讲清它比最小实现多了什么——**测量缓存、滚动补偿、对账、锚点**，而不是只会调 API。

### 16. iOS 上为什么测量后改 `scrollTop` 会出问题？（加分）

iOS WebKit 在惯性滚动中写 `scrollTop` 会取消动量。正确做法是触摸/惯性期间把补偿攒起来，停稳再一次性写回。面试能提到「不能在 momentum scroll 里改 scrollTop」，说明踩过真机问题。

## 白板可以怎么画

口述时画这三层就够：

```
┌ scroll container (overflow:auto, 400px) ── scrollTop
│  ┌ sizer (height = 10000 * 35) ─────────── 骗出滚动条
│  │     [空]
│  │     item 120  translateY(start)
│  │     item 121
│  │     item 122   ← 只渲染 startIndex~endIndex ± overscan
│  │     [空]
```

公式就写两个：

- 固定：`index = floor(scrollTop / h)`
- 不定：前缀和 + 二分 `start[i] <= scrollTop`
