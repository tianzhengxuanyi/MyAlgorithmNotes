# Module Federation（模块联邦）高频面试题

> 背景：模块联邦是 Webpack5 原生能力；Vite 生态通过 `@module‑federation/vite` 插件实现模块联邦；你的简历写了**Module Federation微前端改造**，属于中高级前端高频考点。
> 考察重点：核心概念、运行时原理、共享依赖、版本冲突、隔离问题、Vite适配、业务踩坑。

## 1、什么是 Module Federation（模块联邦）？解决什么问题？

**考察方向：基础概念**

> 简答：Module‑Federation 是 Webpack5 推出的微前端方案，实现**多个独立构建的应用之间可以在运行时互相共享代码、组件、逻辑**。

- `Host`（宿主应用）：主应用，加载远程模块；
- `Remote`（远程应用）：子应用，向外暴露模块组件。

解决的痛点：

1. 传统微前端（qiankun、single‑spa）更多是**应用级沙箱隔离**，模块联邦做到**模块粒度共享**；
2. 子应用可以独立构建、独立部署，运行时动态拉取远程模块，不需要编译期合并代码；
3. 公共依赖可以做 shared 共享，避免多个应用重复打包相同库，减少包体积。

> 区分：qiankun 是**应用沙箱**；Module Federation 是**代码模块共享机制**，两者可以搭配使用。

## 2、Module Federation 核心配置字段分别是什么？（host / remote / exposes / remotes / shared）

**考察方向：基础配置理解**

- `name`：当前应用全局唯一名称，remote 会引用这个名字；
- `filename`：remote 构建输出的远程入口文件，一般 `remoteEntry.js`；
- `exposes`（remote子应用）：向外导出哪些模块/组件，供host消费；`'./Component':'src/Component.vue'`
- `remotes`（host主应用）：声明要加载哪些远程子应用；配置远程应用名称 + remoteEntry地址。
- `shared`：配置**共享依赖**，如 vue、vue‑router、pinia；多个应用之间复用同一套依赖。

伪配置示例

```js
// Remote子应用
new ModuleFederationPlugin({
  name: "subApp",
  filename: "remoteEntry.js",
  exposes: {
    "./UserPicker": "./src/components/UserPicker.vue",
  },
  shared: ["vue", "pinia"],
});

// Host主应用
new ModuleFederationPlugin({
  name: "hostApp",
  remotes: {
    subApp:
      "subApp@[http://localhost:3002/remoteEntry.js](http://localhost:3002/remoteEntry.js)",
  },
  shared: ["vue", "pinia"],
});
```

## 3、shared 共享依赖工作原理？shared 的策略（singleton、eager、requiredVersion、strictVersion）

**考察方向：高频必问，简历写过模块联邦几乎必问**

> 简答：shared 用来声明多个应用可以共用的第三方依赖库（Vue、Vue‑Router），避免每个子应用重复打包。

关键属性：

1. `singleton:true`：**全局单例模式**，整个运行环境只保留一份实例。Vue/Pinia 必须开启singleton，否则会多份Vue实例，响应式失效。

   > 坑：singleton 下版本不一致，会优先加载满足版本范围的一份。

2. `eager:true`：**预加载**；默认remote依赖是异步懒加载，eager=true构建时直接打包进当前应用，不运行时远程拉取。适合必须同步立即使用的模块。

3. `requiredVersion`：声明期望的依赖版本；host和remote版本不匹配时的版本协商。

4. `strictVersion`：版本严格校验开关，默认为`true`；
   - `strictVersion:true`：校验共享容器内版本是否满足`requiredVersion`；不满足会尝试 fallback 加载自身依赖；**若同时开启`singleton:true`，fallback 会被直接阻断，抛出运行时 Error，中断模块执行**。
   - `strictVersion:false`：**跳过 requiredVersion 版本校验；只要全局 shared 容器中已经存在该依赖，remote 直接复用容器已有的实例，不会触发 fallback，不会加载 remote 自身依赖，忽略版本兼容性**。

> 核心坑点：
> 如果不配置shared，每个remote子应用会把vue、pinia全部打包进自己的remoteEntry，造成重复代码，同时出现多份Vue实例，响应式异常、pinia状态隔离失效。

## 4、singleton 为 true，但是 host 和 remote 的 vue 版本不一致会发生什么？怎么处理？

**考察方向：版本冲突，业务真实踩坑**

> 简答：

1. `singleton: true` 的目标：整个运行环境全局**只允许存在一份该依赖实例**。
2. `strictVersion: true`（默认开启，开启语义版本校验）
   - 场景 1：全局 shared 容器已存在依赖，**且版本满足 remote 的 `requiredVersion`**：直接复用容器中 host 提供的库版本，正常运行。
   - 场景 2：全局 shared 容器已存在依赖，**但是现有版本不满足 remote 的 requiredVersion**：
     1. strictVersion 检测出版本不兼容，尝试 fallback，想要加载 remote 自身携带的依赖版本；
     2. 受 `singleton:true` 的约束，禁止载入第二份实例，fallback 路径被阻断；
     3. **抛出运行时错误 `Shared module ... doesn't satisfy requiredVersion`，直接中断该远程模块的执行。**
3. `strictVersion: false`
   - 完全跳过 `requiredVersion` 语义版本校验；
   - **只要全局 shared 容器已经存在该依赖实例，无论版本号是否匹配，remote 直接复用这份已有的实例，不会触发 fallback，不会抛出异常。**
   - 风险：版本差异过大时，API 接口不兼容，后续业务逻辑运行时报错。
4. 风险总结：
   - `singleton:true + strictVersion=true`：版本不匹配 → **抛出运行时错误，远程模块直接执行失败**；
   - `singleton:true + strictVersion=false`：强制复用已有实例，无框架层面报错，但承担版本 API 不兼容业务风险。

解决方案：

1. 团队统一锁定核心库版本，从根源规避版本差异；
2. shared 配置`requiredVersion`明确版本范围，使用默认`strictVersion:true`做校验；
3. 迫不得已允许版本混用：设置`strictVersion:false`放宽版本校验，业务上要做版本兼容性测试；
4. 实在无法统一，关闭 singleton，接受多实例（**Vue生态尽量不要，会破坏响应式、Pinia状态**）。

> 补充你的追问确认：**strictVersion: false 不是强制重新加载，恰恰相反：只要shared全局容器已经存在该依赖，remote就直接复用已有实例，不会再加载remote自带的依赖**；牺牲版本安全换取单实例，业务要承担API不兼容风险。

## 5、remoteEntry.js 的作用，里面存了什么？

**考察方向：运行时原理**

> 简答：remoteEntry是remote子应用构建产出的入口文件。

1. 里面包含：remote的模块映射表、exposes导出模块地址、shared依赖信息；
2. host在运行时通过JSONP动态加载这个remoteEntry脚本；
3. 加载完成后 host 就可以读取 remote 的模块清单，动态import远程组件。

## 6、模块联邦加载远程模块完整执行流程？

**考察方向：运行时流程口述题**

1. Host应用启动，读取remotes配置；
2. 浏览器通过JSONP动态请求远程子应用的 `remoteEntry.js`；
3. remoteEntry执行，把remote的模块信息注册到webpack的共享容器`__webpack_share_scopes__`；
4. Host执行`import("subApp/Component")`；
5. 解析：优先检查shared共享scope中是否存在依赖；缺失则加载对应shared库；
6. 拉取remote中exposes对应的组件chunk；执行渲染。

> 全局共享存储对象：`window.__webpack_share_scopes__`，所有应用共享这个全局对象。

## 7、Module Federation 有哪些常见的问题？

**考察方向：业务踩坑，面试重点，你项目中也遇到过**

1. **依赖版本冲突**：shared版本不一致，singleton模式API不兼容；开启`strictVersion:false`会跳过版本校验，有API不兼容风险；
2. **多实例问题**：没有开启singleton，产生多份Vue/Pinia实例，响应式、状态管理异常；
3. **开发环境联调麻烦**：线上远程Entry和本地源码切换；（对应你项目：自定义Vite插件做本地源码替换）
4. **样式隔离问题**：模块联邦本身**没有提供CSS隔离**，需要CSS Module / scoped / CSS变量 / BEM避免样式污染；
5. **错误堆栈、sourceMap混乱**：远程模块的sourceMap地址跨域；
6. **远程应用服务挂掉，host直接报错崩溃**；需要做远程模块加载异常捕获容错；
7. 类型丢失：远程组件TS类型丢失，需要d.ts手动导出共享类型。

## 8、Vite 如何使用 Module Federation？和 Webpack5模块联邦有什么区别？

**考察方向：你的项目使用Vite+Module‑Federation，高频追问**

> 简答：

- Webpack5：原生内置 ModuleFederationPlugin；
- Vite：没有内置，使用第三方插件 `@module‑federation/vite`，是社区兼容实现；
- 运行时输出的remoteEntry格式**尽量对齐webpack**，可以实现Vite Host ↔ Webpack Remote互相调用；

> 你的业务场景：开发环境自定义Vite插件，把线上remoteEntry远程模块，替换成本地Monorepo源码，实现本地联调。
> 坑点：Vite模块联邦插件部分webpack高级特性支持有限，shared、singleton、strictVersion机制逻辑大体相同。

## 9、Module Federation 和 qiankun / single‑spa 的区别？什么场景选哪个？

**考察方向：选型对比**

| 对比项   | Module Federation                                | qiankun(single‑spa)                    |
| -------- | ------------------------------------------------ | -------------------------------------- |
| 粒度     | **模块粒度**：共享组件、函数；应用也可以完整暴露 | **应用粒度**：整个子应用HTML页面挂载   |
| 沙箱     | **无JS沙箱**，没有隔离；需要自己处理全局变量污染 | JS沙箱（快照/Proxy沙箱）、样式隔离能力 |
| 构建     | 子应用独立构建输出remoteEntry                    | 子应用正常构建，不需要特殊plugin       |
| 通信     | 通过shared共享状态、导入导出模块                 | 全局事件、props通信                    |
| 适用场景 | 多个团队组件复用，模块共享；Monorepo多子应用     | 完整页面级微前端，遗留系统接入         |

> 补充：两者可以组合使用：qiankun做页面应用隔离，模块联邦做组件代码共享。

## 10、模块联邦中，如何做远程模块加载失败容错降级？

> 简答：

1. import远程模块使用动态import + try‑catch捕获异常；
2. 使用Vue的`defineAsyncComponent`错误边界，远程组件加载失败展示降级占位UI；
3. 可以配置备用CDN remoteEntry地址，主地址失败切换备用。

```js
// Vue伪代码示例
const RemoteComp = defineAsyncComponent({
  loader: async () => {
    try {
      return await import("subApp/UserPicker");
    } catch (e) {
      console.error("远程模块加载失败", e);
      return await import("./DefaultFallback.vue");
    }
  },
  loadingComponent: Loading,
  errorComponent: ErrorFallback,
});
```

## 11、exposes 可以导出多个组件吗？可以导出工具函数/hooks吗？

> 简答：可以。`exposes`不仅可以导出vue组件，也可以导出hooks、工具函数、常量、store模块。remote只需要把文件路径配置进去，host就可以import消费。

## 12、shared中 eager:true 使用场景与弊端？

> 简答：

- 使用场景：某些模块需要**同步直接使用**，不能异步；eager会把依赖打包进当前bundle，不运行时远程拉取。
- 弊端：eager=true的shared依赖，会增大当前应用打包体积；慎用，不要大量开启eager。

## 13、什么场景不适合使用 Module Federation？

> 简答：

1. 简单项目，子应用少，直接Monorepo内部包引用即可，引入模块联邦增加复杂度；
2. 需要强JS运行沙箱隔离（第三方不可信子应用），模块联邦没有JS沙箱，优先qiankun；
3. 老旧低版本webpack4项目，不能原生支持，需要额外垫片。

## 14、你项目中Module‑Federation遇到过什么实际问题，怎么解决？（简历项目必准备口述题）

> 参考口述（贴合你的JH4J项目）
> “项目基于Module Federation做微前端改造，遇到两个典型问题：
>
> 1. **shared依赖版本冲突问题**，host与子应用vue/pinia版本不一致，开启singleton:true，默认strictVersion严格校验，版本不匹配会加载子应用自身vue实例，产生多份实例，响应式异常；优先团队统一锁定核心库版本，配置singleton:true + requiredVersion版本协商；万不得已才关闭strictVersion，同时要做API兼容性回归测试。
> 2. **本地开发联调困难**：host默认加载线上子应用remoteEntry，不方便本地调试子应用。于是开发自定义Vite插件，开发环境拦截远程模块请求，替换为Monorepo本地源码，实现本地多子应用联调，同时做构建优化，降低构建耗时。
> 3. 同时注意模块联邦没有自带样式隔离，业务使用scoped、css‑module规避样式互相污染。”
