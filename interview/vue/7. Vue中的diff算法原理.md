# Vue中的diff算法原理

## 简答

Vue diff 算法，我从前提约束、算法演进、核心思想三部分来讲：

## 一、前提条件

1. **同层比较**：diff 只在 VNode 树同一层级对比，不跨层级移动 DOM。完整树 diff（支持跨层移动）理论复杂度 O (n³)，业务中跨层级移动 DOM 极少；Vue 放弃跨层比对，将同层列表 diff 复杂度降到 O (n)，用极小代价换取巨大性能收益。
2. **key 作为节点唯一标识**：key 是节点身份，用来建立新旧节点映射，实现 DOM 复用。不写 key 时 Vue 使用就地复用策略，按下标比对；列表中间增删节点，会发生错误复用，产生大量不必要 DOM 更新。
3. **核心目标**：最小化真实 DOM 操作，DOM 操作会触发回流重绘，是渲染瓶颈。

## 二、算法演进

### 1. 简单 Diff（单端 Diff，Vue 早期方案，未正式使用）

遍历新列表，维护`maxIndex`记录遍历过旧节点的最大索引。找到对应节点，如果旧索引小于 maxIndex，代表节点顺序错乱，需要移动。
缺点：仅适合尾部追加；头部插入场景，所有后续节点都会被误判为需要移动，DOM 开销大。但 maxIndex 思想是后续 diff 基础。

### 2. 双端 Diff（Vue2 使用）

设置四个指针：旧头、旧尾、新头、新尾，向中间收拢。按优先级依次比对：旧头 vs 新头、旧尾 vs 新尾、旧头 vs 新尾、旧尾 vs 新头。命中则更新对应节点，移动指针。
四种比对都不命中时，拿新头 key 去旧列表查找：

- 找到节点：移动到旧头位置，旧列表该位置置空避免重复比对；
- 找不到：代表新增节点，挂载到旧头前。
循环结束后：旧列表剩余节点卸载；新列表剩余节点新增。
优点：头尾增删场景性能好；缺点：中间大量乱序场景，DOM 移动操作偏多。

### 3. 快速 Diff（Vue3 使用）

分为五步：
① 前后缀预处理：从头尾双向比对，匹配到相同 key 节点直接 patch，缩小中间待处理区间；
② 建立 keyToOldIndex 映射表，遍历新列表中间区域，判断节点是否为新增；
③ 构建 source 数组：source 下标对应新列表中间节点下标，source 值存放对应节点在旧列表的下标；不存在则填 - 1；
④ 求最长递增子序列 LIS：source 数组中 LIS 对应的节点，代表在旧列表里相对顺序不变，**不需要移动**；其余节点需要移动；
⑤ **倒序遍历 source 数组**：

- source [i] === -1：新增节点，挂载在锚点前；
- source [i] !== -1，不在 LIS：移动节点；
- source [i] !== -1，在 LIS：节点不动。
倒序原因：`insertBefore`依赖后面节点作为锚点，从后往前处理保证锚点已存在。
优势：乱序长列表场景下，最大程度减少 DOM 移动次数；极端完全乱序场景，会退化完整执行全部逻辑。

## 三、核心思想总结

Vue2 双端 Diff 依靠四指针头尾优先比对；Vue3 快速 Diff，预处理首尾节点，配合 LIS 找出无需移动节点。
两者共同点：同层比对、依靠 key 复用 DOM、目标最小化 DOM 操作。
Vue3 额外还有编译期优化：`patchFlag`标记动态节点 + `Block Tree`，静态节点直接跳过 diff，进一步减少比对范围。

一句话总结：diff 本质是在同层级列表里，借助 key 找到可复用 DOM，用最少移动 / 新增 / 删除操作完成新旧列表更新。

## 四个关键词（卡住就说这四个）

1. **同层 + key**：身份对上才复用 `el`。
2. **Vue2 双端**：四种头尾比，头插/尾插便宜。
3. **Vue3 快速 Diff**：稳定前后缀先剥掉，中间用 LIS 少搬。
4. **LIS**：最长递增下标 = 相对位置没变，可以不动 DOM。

---

## 共同前提

`patch` 里 type/key 相同才会比 children。两边都是数组才 Diff。

- `sameVnode` / `isSameVNodeType`：`type` 与 `key` 都相等。
- 找到可复用：`patch` 更新 props/文本，必要时移动真实 DOM。
- 新有旧无：mount；旧有新无：unmount。
- 不用 index 当列表 key，否则插入删除后会对齐错节点。

## 简单 Diff（铺垫，知道缺陷即可）

遍历新节点，旧数组里找相同 key。记下已处理过的最大旧下标 `maxIndex`：

- 当前旧下标 `>= maxIndex`：相对顺序仍递增，只 patch，抬高 `maxIndex`。
- 当前旧下标 `< maxIndex`：相对前面逆序，要把 DOM 插到上一个新节点后面。

头插时旧节点下标全变小，后面几乎都会移动。所以生产不用。

---

## Vue2：双端 Diff

```
oldStartIdx / oldEndIdx
newStartIdx / newEndIdx
```

循环里按固定顺序比（key 相同才算命中）：

1. 旧头 vs 新头 → 原地 patch，两头指针 ++
2. 旧尾 vs 新尾 → 原地 patch，两尾指针 --
3. 旧尾 vs 新头 → patch，**旧尾 DOM 挪到旧头前面**
4. 旧头 vs 新尾 → patch，**旧头 DOM 挪到旧尾后面**

四种都不中：在旧列表找新头的 key；找到就挪到旧头前并置 `null`；找不到当新增，插在旧头前。

结束：`start > end`。新侧还有剩余 → 批量 mount；旧侧还有 → 批量 unmount。

头插、尾插往往一次头尾命中就结束，比简单 Diff 少很多移动。中间整段打乱时，第四步之后的「在旧数组里搜」会频繁搬节点。

---

## Vue3：快速 Diff

源码 `patchKeyedChildren`，三步：

**1. 预处理前后缀**

从左扫到 key 不同为止，能对齐的直接 patch。再从右同样扫。剩下中间两段乱序区间。

若旧中间已经空了 → 新中间全是新增。若新中间空了 → 旧中间全删。

**2. 中间：映射 + source**

`keyToNewIndexMap`。扫旧中间节点：key 不在新区间就 unmount；在就 patch，并记下「它在新中间里的下标」到 `source` 数组（0 表示没对上）。

**3. 最长递增子序列**

`getSequence(source)` 得到「不用移动」的那些新下标。倒序扫新中间：

- 下标在 LIS 里：DOM 相对顺序对，不 insert。
- 否则：挂到「下一个已处理新节点」前面当锚点。

LIS 的含义：在一组新下标里找出最长的递增序列，这些节点相对次序没变，搬剩下的次数最少。

## 对比（必背）

| | 简单 | Vue2 双端 | Vue3 快速 |
|---|---|---|---|
| 稳定头尾 | 头插很差 | 四种命中，头尾插入好 | 前后缀直接跳过 |
| 中间乱序 | 容易全搬 | 仍可能多搬 | LIS 压最小移动 |
| 无 key | 按下标 | 按下标 | `patchUnkeyedChildren` 按下标 |

Vue3 列表 Diff 换算法；另外编译器让大量静态节点根本不走进 `patchKeyedChildren`。手写 `h()`、动态结构没有 `patchFlag` 时，仍走完整快速 Diff。

## 可能被追问

**Q：为什么不跨层比？**

树编辑距离太贵。跨层当成卸旧挂新，组件状态会丢。见第 5 题。

**Q：最长递增子序列为什么能少搬 DOM？**

`source[i]` 是「新列表位置」。若 1,3,5 递增，说明这几个节点相对前后关系没变，真实 DOM 上本来就挨着对的顺序，再 insert 是浪费。把不在序列里的（逆序的）插到正确锚点即可。

**Q：Vue3 预处理像不像双端？**

只做「从头/尾连续相同就 patch」，不做「旧尾对上新头就移动」那四种交叉命中。交叉和乱序交给中间的 LIS。所以不是双端 Diff 换了个名。

**Q：没有 key 的 `v-for` 呢？**

不建 map、不算 LIS，按下标逐个 patch，长度差则尾部增删。不能识别换位，所以会错复用。

**Q：为什么 LIS 能确定不用移动的节点？能不能换别的算法？**

按**新列表从左到右**看，每个节点对应一个旧下标。若这些旧下标是递增的，说明它们在旧 DOM 里的相对前后关系和新列表一致，真实节点本来就排对了，再 `insertBefore` 纯浪费。

要「尽量少搬」，就要在这些旧下标里留下 **最长的一条递增链**，这正是 LIS。key 唯一时，它等价于两条 key 序列的 **LCS**。Vue 的 `getSequence` 用耐心排序，O(n log n)。

能换，但更差或没必要：简单 Diff 的 `maxIndex` 是贪心递增，不是最长，所以头插会多搬；全搬最笨；二分图最小移动杀鸡用牛刀。LIS 在「用 insertBefore 任意插入」这个模型下，留下不动的节点数是最多的。

源码里 `source` 按下标对齐**新**中间节点，值是旧下标（0 表示新增）。LIS 求的是这些**值**的最长递增。

**Q：不写 key 时 diff 发生了什么？就地复用？**

走 `patchUnkeyedChildren`：取 `min(旧长, 新长)`，**按下标** `patch(c1[i], c2[i])`。type 相同就复用第 i 个 DOM 改内容；多出来的旧节点从尾部卸，多出来的新节点从尾部挂。这就是就地复用：**只认位置，不认身份**。

中间插入/删除后，后面每一项下标都错位，A 的 DOM 会被拿去显示 B 的数据（输入框、子组件 state 会串）。列表静态、不插删重排时，就地复用够用。

**Q：双端四种比对为什么是这个优先级？**

原则：**先做不用搬 DOM 的，再做要 insertBefore 的。**

1. 旧头 vs 新头、旧尾 vs 新尾：原地 patch，只动指针。列表最常见是两头稳定、尾部增删，命中率高、成本最低。
2. 交叉比对（头对尾、尾对头）：说明发生了移位，一定要插 DOM，放到后面。

有唯一 key 时，头头和「旧头对新区尾」不会同时成立，顺序不影响正确性。Vue2 源码交叉是先「旧头 vs 新尾」再「旧尾 vs 新头」；书里有时对调，算法都对。面试抓住「先原地、后移动」即可。

**Q：快速 Diff 比双端强在哪？什么场景最明显？**

双端把乱序丢给「拿新头去旧列表搜 + 往旧头前插」，节点可能被多搬。快速 Diff 剥完稳定前后缀后，对中间用 LIS，**一次算出哪些 DOM 可以不动**。

提升最明显：**中间局部乱序**——拖拽排序、打乱、中间插入删除、分页数据换序。头尾追加/删除两者都很快。完全逆序时双端交叉命中反而可能很顺，快速 Diff 的 LIS 可能只留下 1 个，这不是它的主场。

**Q：虚拟 DOM 的 diff 和渲染器 patch 什么关系？diff 是 patch 的子流程吗？**

**是。** `patch` 是写 DOM 的总入口（挂载 / 更新 / 卸载）。diff 特指 **两边 children 都是数组** 时，在 `patchChildren` 里那一段列表对齐（`patchKeyedChildren` / `patchUnkeyedChildren`）。

```
patch(n1, n2)
  type/key 不同 → 卸旧挂新
  相同 → patchElement / 组件
           └ patchChildren
                ├ 文本：改 textContent
                └ 都是数组 → Diff（同层 + key / 就地复用）
```

口语里常把整棵树对比叫 diff；实现上树的递归是 patch，真正叫 Diff 算法的是列表那一段。
