# SSR（服务端渲染）解决了什么问题，Vue 中如何实现

## 简答

普通 Vue 项目默认是 CSR 客户端渲染：浏览器拿到空白 HTML，下载 JS，执行 JS 生成 DOM 渲染页面。爬虫拿到的是空容器，首屏等待 JS 下载解析。
SSR 服务端渲染：在 Node 服务端执行 Vue 组件，直接生成带完整内容的 HTML 字符串返回浏览器；浏览器可以直接展示 HTML，之后下载客户端 JS 包，执行**hydration 水合**：复用已经存在的 DOM，绑定事件，建立 VNode 和 DOM 映射，页面变成可交互 SPA。一套组件代码两端运行，称为**同构**。

## 解决的问题

1. **SEO 优化**：服务端返回带真实业务内容的 HTML，搜索引擎爬虫可以直接抓取内容；虽然现代爬虫支持执行 JS，但 SSR 收录稳定性更好。
2. **首屏加载速度**：弱网、低端设备，不用等待 JS 下载解析即可看到页面内容，提升首屏 FP。

## Vue SSR 实现思路

Vue SSR 分为**服务端入口**和**客户端入口**两个 bundle：

1. 服务端：调用`createSSRApp`，组件渲染生成 HTML 字符串，**不会挂载 DOM、不绑定事件**；渲染前完成数据预取，拿到数据再渲染组件。
2. 客户端：调用`createApp`，使用`hydrate`模式，复用服务端返回的 DOM，绑定事件，接管页面后续交互；客户端 VNode 必须和服务端渲染 HTML 结构一致，否则会报水合不匹配错误。

> 
> 项目一般不会手写原生 SSR 配置，大多直接使用 Nuxt 框架，自动处理双入口、路由、数据预取、缓存等。

## SSR 代价与限制

1. 消耗服务器 CPU，高并发场景需要页面缓存、组件缓存优化；
2. 代码要兼容两端环境：**setup 顶层不能直接访问 window/document**，只能在客户端钩子（onMounted）里使用浏览器 API；
3. 水合阶段有额外 JS 开销；页面跳转依然是 SPA 跳转。

一句话总结：SSR 在服务端把组件渲染成带内容 HTML 返回浏览器；客户端执行水合复用 DOM 绑定事件；核心收益 SEO 与首屏 FP，代价是服务器开销与代码同构约束。

## 四个关键词（卡住就说这四个）

1. **renderToString / 流式渲染**：组件树 → HTML。
2. **hydration**：复用服务端 DOM，绑上事件和响应式。
3. **同构**：两端共享组件，环境 API 要分流。
4. **Nuxt**：工程化 SSR/SSG，而不是手写两个入口这么朴素。

---

## 和 SPA、传统服务端模板的区别

- **JSP / 早期 PHP**：整页服务端拼 HTML，交互弱，每次跳转整页刷新。
- **纯 SPA**：体验好，首屏和 SEO 差。
- **Vue SSR**：首屏 HTML 来自服务端，激活后路由、状态仍是前端接管，后续导航可以继续 CSR。

打开「查看源代码」：SPA 几乎是空壳；SSR 能看到文章标题、列表这些真实节点。

## Vue 里怎么做（原理级，不绑死某一版 API 名）

**服务端入口**

用 `@vue/server-renderer`（Vue3）或 `vue-server-renderer`（Vue2）：

- 创建应用（Vue3：每次请求 `createApp` 一次，**禁止单例 app 跨请求共享**，否则 state 串了）
- 可选：等 router `isReady`、预取数据写入 store
- `renderToString(app)` 得到 HTML；或 `renderToNodeStream` 边生成边吐，降低 TTFB
- 把 HTML 塞进模板，顺带内联 `window.__PINIA__ = ...` 之类状态，避免客户端再闪一次空数据

**客户端入口**

同样的根组件 `createApp`，调用 `app.mount` 时若容器里已有服务端标记，走 **hydrate**：

- 不对节点做「删了重建」
- 按 VNode 和现有 DOM 比对，不一致会警告（hydration mismatch）
- 补事件监听，恢复响应式，之后 patch 与 CSR 相同

**数据预取**

服务端在渲染前把首屏接口跑完。组件侧常见约定：`setup` 里的请求要能在 Node 跑（用 isomorphic fetch）；或 Nuxt 的 `useAsyncData` / `useFetch` 帮你把结果序列化到客户端。只写在 `onMounted` 里的请求 **服务端不会跑**，首屏 HTML 里就没有这块数据。

## 实践形态

- **手写 Node + Express/Koa**：适合讲原理，生产要自己处理缓存、错误、内存泄漏。
- **Nuxt**：约定式路由、SSR/SSG/hybrid、自动 payload。现在项目里「做过 SSR」多半指这个。
- **SSG**：构建期渲染成静态 HTML（文档站、营销页），运行时没有 Node 渲染成本，也算广义的「先有 HTML」。

---

## 坑（面试加分）

- **生命周期**：服务端没有 DOM，不跑 `beforeMount` / `mounted`。副作用、定时器、第三方只认浏览器的库，放客户端钩子或 `import.meta.client` 判断。
- **跨请求状态污染**：Vuex/Pinia 必须 **每请求新实例**。
- **mismatch**：服务端 `new Date()`、`Math.random()`、浏览器宽度、`v-if` 依赖 `window` 都会导致激活失败，页面闪烁或整段重挂。
- **不是银弹**：算力在服务器；要缓存 HTML / CDN；纯后台管理系统没 SEO 需求，SSR 往往不划算。首屏还可以用骨架屏、SSR 部分路由、CSR + 预渲染折中。

## 可能被追问

**Q：hydration 和 mount 的区别？**

mount 从空容器建 DOM；hydrate 认为 DOM 已经在那儿，只绑定。DOM 对不上就会退化成警告 + 可能局部重渲染。

**Q：SSR 一定更快吗？**

用户感知首屏通常更好；服务器耗时、网络 RTT、缓存策略决定 TTFB。SSR 很慢时，用户照样白屏，只是白的是等 HTML 而不是等 JS。

**Q：Vue3 的 `ssrRender` 快路径？**

编译器给组件生成面向字符串拼接的函数，少创建完整 VNode 树，这是 Vue3 SSR 性能的一部分，和客户端 patchFlag 是同一套「编译器告诉运行时怎么少干活」。

**Q：什么是 hydration mismatch？什么场景会出现？怎么排查？**

服务端吐出的 HTML 和客户端第一次 `render` 的 VNode **对不上**。hydrate 按预期节点去绑事件，发现 tag、文本、节点个数不一致，就报 mismatch，严重时那段会丢弃服务端 DOM 再走一遍客户端 mount，首屏闪一下。

常见场景：

- 两端 `new Date()`、`Math.random()`、`typeof window` 写出不同模板
- 用了只在浏览器有的宽度、`localStorage` 决定 `v-if`
- 无效 HTML（`<p>` 里再塞 `<div>`）被浏览器改写了树，和 VNode 不一致
- 服务端没把预取数据序列化到客户端，客户端首屏是空列表
- 时区、locale 格式化文本不同

排查：开开发环境看控制台精确 diff；保证预取 state 注入 `window.__PINIA__` 一类 payload；浏览器-only 逻辑放 `onMounted`；检查是否非法嵌套标签。生产可开 hydration mismatch details 看具体节点。

**Q：SSR 的数据请求放在哪里？服务端和客户端分别什么时候请求？**

**不要只写在 `onMounted`**：服务端不跑 mounted，HTML 里就是空的。

正确：

- 服务端在 `renderToString` **之前**把首屏数据拉完（路由 `beforeResolve`、组件 `setup`/`async setup`、`onServerPrefetch`、Nuxt `useAsyncData`）
- 把结果序列化进 HTML
- 客户端 hydrate 时 **用这份 payload 当初始 state**，不再打一遍同样的首屏请求（或 Nuxt 会判断 payload 已有就跳过）
- 交互之后的请求仍然只在客户端

同构组件里 `setup` 两端都会执行：服务端跑一遍用于渲染，客户端再跑一遍用于激活。请求函数必须能在 Node 里跑（不能碰 `window`），并用 payload 去重，避免 double fetch。

**Q：createSSRApp 和 createApp 的区别？**

都是造应用，但渲染器入口不同：

- `createApp`：`mount` 走 **创建 DOM**（`createElement`）
- `createSSRApp`：客户端 `mount` 走 **hydrate**，复用页面上已有节点

服务端用 `createSSRApp` + `renderToString` 也行（Vue3 推荐两端都用 createSSRApp，保持实例行为一致，例如 `emits` 声明）。客户端若误用 `createApp` 去挂已经有 SSR HTML 的容器，会 **清空重挂**，等于白做服务端渲染。

**Q：SSR 和 SSG 静态站点生成的区别？**

| | SSR | SSG |
| --- | --- | --- |
| 何时出 HTML | **每个请求** Node 现算 | **构建期**算一次，产出静态文件 |
| 数据 | 可按用户、按 Cookie 变 | 适合全站相同的内容 |
| 成本 | 要 Node 常驻、要缓存 | CDN 静态文件，便宜 |
| 典型 | 后台个性化、实时库存 | 文档、博客、营销页 |

Nuxt 还可以混合：部分路由 SSR，部分 SSG。SSG 也要客户端 hydration 才能交互，只是 HTML 不是请求时现生成。

**Q：服务端环境为什么不能直接使用 window？**

Node 没有浏览器全局对象：`window` / `document` / `localStorage` 都是 `undefined`，一访问就抛错，整次 `renderToString` 失败，用户拿到 500。

即便判断了 `typeof window !== 'undefined'`，也别用它在 **首次 render** 里决定 DOM 结构，否则两端 VNode 不一致，变成 mismatch。访问浏览器 API 放到 `onMounted`，或拆 `.client.ts` 插件。
