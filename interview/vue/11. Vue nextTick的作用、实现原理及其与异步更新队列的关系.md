# Vue nextTick 的作用、实现原理及其与异步更新队列的关系

## 简答

Vue DOM 更新是异步的。数据发生变化不会立刻执行 patch 更新 DOM；而是把组件更新函数包装成 job，推入调度器 job 队列，做去重处理，同一个组件多次修改只保留一次更新任务。等到当前同步代码全部执行完毕，在微任务中批量执行 job，一次性更新视图。
`nextTick`的作用：**等待本轮 DOM 更新完成之后执行回调**，修改数据后想获取最新 DOM，就需要用 nextTick。

1. 为什么采用异步队列
如果同步更新 DOM，循环多次修改响应式数据会触发多次 patch，带来大量 DOM 开销。异步 + job 去重，只拿最终状态渲染一次，提升性能。
2. 实现原理
nextTick 内部维护一个回调数组。多次调用 nextTick，回调都会存入这个数组。内部基于 Promise 创建微任务（Vue2 有降级：MutationObserver/setImmediate/setTimeout；Vue3 仅使用 Promise）。

> 
> 注意：调度器刷新 job 的 Promise 和 nextTick 的 Promise 不是同一个实例，只是都属于微任务，遵循固定执行时序：
> 同步代码 → job 入队 → 微任务执行 flushJobs（执行所有组件 update，patch DOM） → 微任务执行 nextTick 队列中的所有回调。

3. nextTick 和异步更新队列（scheduler）的关系
两者属于同一套事件循环时序，但职责分离：

- scheduler：负责收集组件更新 job，在微任务批量更新 DOM；由响应式 trigger 触发；
- nextTick：独立维护回调队列，等待 scheduler 本轮 DOM 更新完成后再执行用户回调。

一句话总结：数据变更把组件更新任务推入调度队列，微任务批量更新 DOM；nextTick 的回调会在本轮 DOM 更新完成之后执行，用于获取最新 DOM。
---

## 四个关键词（卡住就说这四个）

1. **异步更新队列**：变更不立刻渲染，job 先排队。
2. **去重**：同一组件同一轮只保留一个 job。
3. **微任务 flush**：默认 `Promise.then`，比 `setTimeout` 更早、更稳。
4. **nextTick 挂在 flush 之后**：用来读更新后的 DOM，不是用来「触发更新」。

---

## 执行流程（按时间线背）

以组件里连续改三次 `message`，再 `await nextTick()` 读 DOM 为例。

**1. 同步阶段**

三次赋值都走 Proxy set → `trigger` → scheduler。`queueJob` 发现这个 `update` 已经在队列里，不再重复 push。`queueFlush` 只安排一次微任务。

**2. 同步代码结束**

此时真实 DOM 还没动。你如果同步 `querySelector`，读到的是旧树。

**3. 微任务：flushJobs**

按队列执行 job（组件 `update` → render → patch）。同一轮里 watch 的 `pre` 在组件更新前，`post` 在 DOM 更新后。

**4. nextTick 回调**

flush 对应的 Promise resolve，你的 `fn` 执行，DOM 已是新的。

一句话串起来：**同步只入队，微任务才 patch，nextTick 读的是 patch 之后。**

## Vue2 vs Vue3（实现差异，面试常问）

**Vue2**：自己维护 `callbacks` 数组 + `pending` 锁。`timerFunc` 按环境降级：`Promise.then` → `MutationObserver` → `setImmediate` → `setTimeout`。用户 `nextTick(cb)` 就是把 cb 推进同一个 callbacks，和视图更新共用这一套。

**Vue3**：调度器更干净。`queueJob` / `queuePostFlushCb` 分队列；`currentFlushPromise = Promise.resolve().then(flushJobs)`。`nextTick(fn)` 本质是 `currentFlushPromise.then(fn)`，没有 flush 时就 `Promise.resolve().then(fn)`。现代环境几乎只靠 Promise，不再强调那一长串降级。

**为什么优先微任务而不是宏任务**：宏任务（`setTimeout(0)`）要等完本轮事件、渲染、I/O 才跑，中间用户可能已经看到一帧旧 DOM，或穿插进别的任务。微任务紧跟当前同步代码，更新更及时，也和浏览器更新时机更贴。

## 可能被追问

**Q：数据频繁变化为什么通常只更新一次视图？**

同一组件的 `update` 在队列里用引用去重；flush 前改 100 次，渲染函数只跑一次，用的是最后的数据快照。

**Q：nextTick 里再改数据会怎样？**

会开启**下一轮** queueFlush，再走一次更新。不要在 `updated` / `nextTick` 里无条件改会触发渲染的数据，容易死循环。

**Q：`flush: 'sync'` 的 watch 还走 nextTick 吗？**

不走。sync 在 trigger 时立刻跑。默认 `pre`、`post` 才进异步队列。

**Q：和 `process.nextTick` 是一回事吗？**

不是。Node 的 `process.nextTick` 是它自己的队列，比 Promise 微任务还靠前。Vue 的 nextTick 是框架的 DOM 更新调度 API。

**Q：nextTick 是宏任务还是微任务？Vue2/Vue3 实现差异？**

**优先微任务。** 默认 `Promise.then`，跟在本轮同步代码后面、排在 `setTimeout` 前面。

Vue2：`callbacks` 数组 + `pending`。`timerFunc` 按环境降级：`Promise.then` → `MutationObserver` → `setImmediate` → `setTimeout`（最后这一档才是宏任务）。视图更新和用户 `nextTick` **共用**这一套回调数组。

Vue3：现代环境几乎只靠 Promise。调度器用 `queueFlush`：`currentFlushPromise = Promise.resolve().then(flushJobs)`。用户 `nextTick(fn)` 是 `currentFlushPromise.then(fn)`；本轮没有 flush 时退回同一个 `resolvedPromise.then(fn)`。`queuePostFlushCb`（`updated`、`watch flush:post`）在 `flushJobs` 里跑完 job 之后、用户 nextTick 之前。

**Q：如果在 nextTick 回调里面修改数据，会发生什么？**

本轮 DOM 已经 patch 完了。再改响应式数据会 `queueJob`，因为 `isFlushing` 已结束，会 **再开一轮** `queueFlush`，下一个微任务再更新一次视图。再在那一轮的 nextTick 里改，就再来一轮。无条件改会触发渲染的数据，等于自己套娃，严重时卡死。有终止条件（新旧值比较、只改一次）才能写。

**Q：job 队列和 nextTick 回调队列的执行顺序？**

同一轮固定是：

```
同步代码（trigger → queueJob）
  → 微任务 flushJobs：pre 队列 → 组件 update/patch → post 队列（onUpdated、flush:post）
  → 再微任务：用户 nextTick 回调
```

所以 nextTick 里一定能读到 **本轮** 更新后的 DOM。`watch` 默认 `pre` 比组件渲染早；`flush: 'post'` 和 `updated` 比用户 `nextTick` 早一截（都在 flushJobs 内）。

**Q：为什么多次调用 nextTick 不会创建多个微任务？**

要分开说：

- **flush 本身**：`isFlushPending` / Vue2 的 `pending`，同一轮只 `Promise.then(flushJobs)` **一次**。这是「多次改数据、多次 nextTick 也不会反复安排更新」的核心。
- **Vue2 的用户回调**：都推进 `callbacks`，只起一次 `timerFunc`，一次微任务里 `for` 跑完。所以多次 `nextTick` **真的只有一个微任务**。
- **Vue3 的用户回调**：每个 `nextTick(fn)` 会在 flush Promise 上再 `.then(fn)`，**会多几个微任务**，但都排在 `flushJobs` 之后，不会重复 flush。面试别说成 Vue3 也把用户回调塞进同一个数组只 then 一次——源码不是那样。

**Q：Promise.then、nextTick、setTimeout 的执行先后顺序？**

宏任务永远在本轮所有微任务之后，所以 `setTimeout` 最后。

本轮 **已经有组件更新**（先改了数据）：

```
同步
→ flushJobs（DOM 更新）
→ 同步阶段里注册的普通 Promise.then
→ nextTick 回调（挂在 flush Promise 后面）
→ setTimeout
```

本轮 **没有更新**（`currentFlushPromise` 为空）：`nextTick` 就是 `Promise.resolve().then`，和你手写的 `Promise.then` 比 **谁先注册谁先跑**，两者都早于 `setTimeout`。

口播：**先微后宏；有更新时 nextTick 一定在 patch 之后；没更新时 nextTick ≈ Promise.then。**
