# watch的原理

## 简答

watch 本质是 **effect + scheduler 的封装**：用一个 lazy effect 去「读」source 完成依赖收集，依赖变了不立刻重跑用户逻辑，而是走 scheduler 调 `job`。`job` 里再跑一遍 getter 拿到 **newValue**，和存着的 **oldValue** 一起交给回调。

和 computed 的分水岭：computed 依赖变了只标 dirty，**有人读才算**；watch 依赖变了就（按 flush）**执行副作用**，没有缓存给模板用。

1. **source → getter**  
   函数：直接当 getter。`ref`：读 `.value`。`reactive` 对象：默认 **deep**，`traverse` 递归访问所有属性才能收集到嵌套字段。数组 source 则 map 成多个取值。
2. **首次**  
   非 `immediate`：只 `effect.run()` 拿到 oldValue，**不调回调**。`immediate: true`：立刻 `job()`，此时 oldValue 为 `undefined`。
3. **变更**  
   trigger → scheduler → `job`：先跑上一轮 `onInvalidate` 清理，再 `cb(newVal, oldVal, onInvalidate)`，然后 `oldValue = newValue`。
4. **flush**  
   `sync` 同步；默认 `pre` 进组件更新前的队列；`post` 进 DOM 更新后的队列（`nextTick` 能读到新 DOM）。多次修改同一 tick 会去重，通常只跑一轮 job。

`watchEffect` 没有独立 cb：effect 本身既是收集过程也是副作用，创建时立刻跑，拿不到 oldValue。

一句话：**lazy effect 读 source 收集依赖；scheduler 里跑回调拿新旧值。computed 是懒计算，watch 是依赖变了做副作用。**

---

## 四个关键词（卡住就说这四个）

1. **effect + scheduler**：收集用 getter，执行用 job。
2. **traverse / deep**：对象要递归读一遍，否则只盯根。
3. **old / new**：第一次 run 存旧值，job 里再 run 得新值。
4. **flush + onInvalidate**：控制何时跑、异步怎么作废上一轮。

---

## 执行流程（按时间线背）

`watch(() => obj.foo, (n, o) => {})`

**1. 创建**

把 source 收成 getter。`effect(getter, { lazy: true, scheduler })`。lazy，不自动当副作用跑完整个 cb。

**2. 第一次取值**

`oldValue = effectFn()`。getter 读 `obj.foo` → track，当前 effect 进 `foo` 的依赖桶。此时 **不调用户回调**（除非 immediate）。

**3. `obj.foo` 变了**

trigger 到这个 effect，因有 scheduler，不直接 `effectFn()`，改为排队/同步执行 `job`。

**4. job**

`newValue = effectFn()`（cleanup 旧依赖再收集）。`hasChanged` 才调 cb（deep 或强制时另说）。把 new 存成下一轮的 old。

**5. 停止**

返回的 `stop` 调 `effect.stop()`，从所有 dep 里摘掉，后续 trigger 不再来。

## source 怎么收集

| source | getter | 默认 deep |
|--------|--------|-----------|
| `() => x.foo` | 函数本身 | 否（只收集读到的） |
| `ref` | `() => ref.value` | 值是对象时可 deep |
| `reactive(obj)` | `() => obj` | **是**，要 traverse |
| `[a, b]` | 分别取值组成数组 | 按项 |

`traverse`：递归走对象/数组属性，触发 get，把嵌套 key 都收集上。不加 deep 时 `watch(() => obj, cb)` 只盯对象引用，改 `obj.foo` **不会**触发（引用没变）。Vue 对直接传入的 reactive 对象默认 deep，就是怕这个坑。

---

## 和 computed、watchEffect

| | computed | watch | watchEffect |
|---|---|---|---|
| 目的 | 派生值 | 指定 source 的副作用 | 自动收集的副作用 |
| 何时跑 getter | 读 `.value` | job 里为了拿新值 | 创建时立刻 + 依赖变了 |
| 回调 | 无（就是值） | `cb(n, o, onInvalidate)` | 函数本体，无 old |
| 缓存 | 有 | 无 | 无 |

模板用 computed；请求、和 DOM/存储同步用 watch；「读到啥就依赖啥、不要旧值」用 watchEffect。

## Vue3 源码对应

`apiWatch.ts` 的 `doWatch`：

- `watch` / `watchEffect` / `watchPostEffect` / `watchSyncEffect` 都进这里。
- `ReactiveEffect(getter, scheduler)`，scheduler 按 flush 绑 `job`、`queueJob` / `queuePreFlushCb`、`queuePostFlushCb`。
- `cb` 为空就是 watchEffect：`effect.run()` 即用户函数，里面可以 `onCleanup`。
- Vue 3.4+ `once: true`：回调跑完自动 stop。

Vue2 是实例上的 **user Watcher**（`vm.$watch`），`Dep.notify` 后跑 `watcher.run`，`deep` 同样 traverse；flush 用 `sync` / 默认异步队列。模型一样：收集 + 调度 + 新旧值。

笔记里的实现（`reactive.js`）已经覆盖主干：getter、lazy、job 里先 cleanup 再 cb、flush post 用微任务。

## 可能被追问

**Q：`immediate` / `flush: 'post'`？**

immediate：创建时就 job 一次，oldValue 是 `undefined`。  
`flush: 'post'`：等组件 patch 完再跑，此时能 `ref.offsetHeight`。默认 `pre` 在渲染前，适合在更新前根据数据改别的状态。`sync` 不进队列，一次 `foo++` 就跑一次，失去批处理。

**Q：onInvalidate / `onCleanup` 干什么？**

异步竞态。下一轮 job（或 effect 重新 run、stop）前先执行上一轮注册的清理：设 `expired=true`、`abort()`。否则慢请求后到会覆盖新结果。computed 不要干这个，那是 watch 的活。

**Q：watch 会不会像 computed 一样缓存？**

不会。每次 job 都为了拿新值去跑 getter，然后执行 cb。没有 dirty 跳过计算这一说；`hasChanged` 只决定 **cb 要不要调**（有时值没变，deep 对象仍可能调）。

**Q：组件卸载 watch 还跑吗？**

会 `stop`。组件 effectScope 停掉时，实例上的 watch 一并摘掉，避免卸载后 set 数据还打请求。

**Q：`watch(obj, cb)` 和 `watch(() => obj.foo, cb)`？**

前者（reactive）默认深监听整个对象；后者只收集 `foo`。要深监听某个嵌套又想当函数 source：`watch(() => obj.nested, cb, { deep: true })`。
