# Composition API 与 Options API 的区别及优势

## 简答

Options API 和 Composition API 是 Vue 的两种组织代码的方式。
Options API 是按**选项类型**拆分代码：data、methods、computed、watch、生命周期各自一块。同一个业务功能，状态、方法、侦听会分散在文件不同位置；逻辑复用依赖 mixin，容易出现命名冲突、隐式依赖，变量来源难以追踪。

Composition API（`<script setup>`是语法糖）按**业务功能**组织代码：在 setup 内部，把同一个功能的响应式变量、计算属性、watch、生命周期写在一起；还可以抽离成独立`useXxx`组合式函数，实现逻辑复用。

二者核心区别：

1. 代码组织：Options 按选项分类；Composition 按业务功能聚合；
2. 逻辑复用：Options 靠 mixin，缺点是隐式依赖、命名冲突；Composition 使用组合式函数，导入显式；
3. TS 类型支持：Options 的 this 推导麻烦；Composition API 天然对类型友好；
4. Tree-shaking：Options 是选项对象，打包工具很难剔除无用代码；Composition 都是独立导入函数，未使用代码可以被打包工具摇掉；
5. 执行时机：setup 在 beforeCreate 之前执行，没有 this；两种 API 可以混合使用。

> 
> 注意：Composition API 本身不会带来渲染性能提升，优势在于代码可维护性、复用性、类型支持。小型简单组件用 Options API 依然简洁合适。

一句话总结：Options API 按选项切分代码，复用靠 mixin；Composition API 按业务聚合逻辑，抽成组合式函数，TS 友好、支持 tree-shaking，适合中大型项目。

---

## 四个关键词（卡住就说这四个）

1. **组织方式**：选项类型 vs 功能切片。
2. **复用**：mixin 合并冲突 vs `useXxx` 显式返回。
3. **this vs 闭包**：Options 靠 `this`；Composition 用普通变量，TS 好推。
4. **不是替代生命周期**：`onMounted` 只是换个注册方式，钩子还在。

---

## 逻辑组织（面试主对比）

Options 里一个「表单校验 + 拉取详情 + 埋点」会变成：data 里三摊字段、methods 里三摊函数、watch 再挂三处。读代码要上下跳。

Composition 可以：

```js
// 伪代码
const { form, validate } = useForm()
const { detail, load } = useDetail(id)
onMounted(load)
```

每个 `useXxx` 内部自己有 ref、computed、watch，外面只看到接口。组件变大时，你搜索 `useDetail` 就能拿到这一功能的全部。

---

## 逻辑复用：mixin 的问题 vs composable

mixin（以及 extends）的老问题：

- 来源不清：`this.xxx` 不知道是哪个 mixin 给的
- 命名冲突：两个 mixin 都有 `data.loading`，合并规则难记
- 关系隐式：mixin 还能 mixin，依赖链不直观

`useXxx()`：调用点一眼看见从哪来、返回了什么；变量名由调用方决定，不会悄悄覆盖；TS 能推返回类型。这是 Composition 相对 mixin **最硬**的优势。

mixins 在 Vue3 还可用，官方不推荐作为主要复用手段。

## 和 Options 的能力对照

| 能力 | Options | Composition |
| --- | --- | --- |
| 状态 | `data()` | `ref` / `reactive` |
| 计算 | `computed` | `computed()` |
| 侦听 | `watch` | `watch` / `watchEffect` |
| 挂载后 | `mounted` | `onMounted` |
| 模板 | `this.foo` | setup 返回或 script setup 顶层绑定 |
| 依赖注入 | `provide`/`inject` 选项 | `provide()`/`inject()` 函数 |

`<script setup>` 是编译期语法糖：顶层绑定自动暴露给模板，不必写 `return`，`props` 用 `defineProps`。

**setup 执行时机**：在 `beforeCreate` 之前同步执行一次。这里没有 `this` 指向 Options 那套（`setup(props, ctx)`，`ctx` 有 `emit`、`attrs`、`slots`、`expose`）。异步 setup 是 Suspense 的话题，默认面试按同步说。

---

## 优势边界（别吹过头）

- 性能：同一套响应式和渲染，**不会因为换 API 就快一个数量级**。
- 学习成本：`ref` 要 `.value`，容易漏；`reactive` 解构丢代理。团队不熟时小页面 Options 更直观。
- 两者可混用：Options 里也能 `setup()`。但混用时 `this` 和 setup 返回值怎么合并，要说清楚，项目里最好定一种风格。

## 可能被追问

**Q：为什么 Vue3 还保留 Options？**

迁移成本、心智熟悉、小组件足够用。Composition 是加法不是废除。

**Q：`ref` 和 `reactive` 怎么选？**

基本类型、需要整体替换、想在函数间传递「这个盒子」用 `ref`；一组强相关字段用 `reactive`。实际项目大量用 `ref`，再 `storeToRefs`。

**Q：Composition 怎么替代 `data` 必须是函数？**

每个组件 `setup` 都会跑一遍，`ref` 是这次调用新建的，天然隔离，不存在根实例那种「对象共享」问题。

**Q：和 React Hooks 的区别？**

Vue 的 `setup` **只跑一次**，不是每次 render 都调；不依赖 hooks 调用顺序，也不需要 `useMemo` 防闭包过期。`watch` / `computed` 是独立原语，不是靠对比 deps 数组。

**Q：`<script setup>` 和普通 setup 有什么区别？底层做了哪些编译优化？**

`<script setup>` 是 **编译期语法糖**，运行时没有另一种组件模型。编译器大致会：

1. 整段脚本包进 `setup()`，顶层 `const/let/function` **自动暴露给模板**，不用 `return`。
2. 宏原地替换：`defineProps` / `defineEmits` / `defineExpose` / `defineModel` / `withDefaults` 编成运行时 props 选项和 `expose()`，**这些函数名运行时并不存在**。
3. 顶层 `await` 编成异步 setup，外层要 `Suspense`。
4. 绑定名做静态分析，模板里用到的才保留，有利于 tree-shaking 和提示未使用变量。
5. 默认封闭实例：不 `defineExpose` 的局部变量不出现在 `this` / 父 ref 上。

普通 `setup()` 是运行时选项，要手动 return，可以用 `this` 的时机更晚（setup 里仍然没有 this），和 Options 混写更常见。性能上两者同一套响应式，**快的是少写样板、绑定分析，不是执行快一个数量级**。

**Q：mixin 的缺点，组合式函数是怎么解决这些问题的？**

mixin：来源不清（`this.x` 哪来的）、命名冲突（合并策略难记）、嵌套 mixin 依赖隐式、和 TS 几乎不对付。

`useXxx()`：调用点显式 `const { x } = useXxx()`，名字由调用方定，冲突在局部变量层解决；返回值可推类型；不污染 `this`。本质是普通函数 + 组合式 API，不是框架合并选项。

**Q：setup 中为什么不能使用 this？**

调用 setup 时，Options 的 `data`/`methods`/`computed` 还没初始化，`this` 代理不完整。若允许 `this`，你会在 setup 里读到半成品实例，和「setup 先于 beforeCreate」矛盾。所以 `this` 是 `undefined`，状态用 `ref`，事件用 `ctx.emit`。等 setup 返回后，返回值才合并进实例，Options 钩子里的 `this` 才能看到这些字段。

**Q：组合式函数和普通函数有什么区别？**

普通函数：算数、请求、纯逻辑，在哪调都行。

组合式函数（composable）约定：

- 内部会调 `ref` / `watch` / `onMounted` / `inject` 等 **只能在 setup 同步上下文（或当前 effectScope）里用的 API**
- 命名 `useXxx`，返回响应式状态给模板用
- 每个组件调用一次就创建一份状态（除非你故意做成模块单例）

在普通事件回调里调 `useMouse()` 会失败：没有当前实例，`onMounted` 注册不了。普通 `formatDate()` 没有这个限制。

**Q：两种 API 混用会有什么坑？**

可以混，但不清爽。

- `setup` 先执行，return 的东西会挂到实例上，Options 的 `methods`/`mounted` 里 `this.xxx` 能用；**反过来 setup 里不能 `this.methods`**。
- `data` 和 setup 返回 **同名**，data 会覆盖，开发环境警告。
- 生命周期两边都会跑：`onMounted` 和 `mounted` 都在，顺序是 Composition 注入的 hook 和 Options 钩子按内部数组走，别依赖「谁先谁后」写业务。
- `<script setup>` 再加一个普通 `<script>` 可以写 `name`、`inheritAttrs`，这是官方支持的拆法；不要再在第二个 script 里写一套 data 抢绑定。

项目里选定一种主风格，混用只留给迁代码。
