## 一、章节笔记

### 1. 本章定位

安全性、身份认证与授权通常是一个「复杂而困难」的话题：在许多框架中，仅认证就可能占全部代码的 50% 或更多。FastAPI 提供多种工具，让你以标准方式轻松处理安全，而不必深研所有安全规范。本章先厘清术语，后续章节再动手实现。

### 2. OAuth2

**OAuth2** 是一个规范，定义了处理认证与授权的多种方法，涵盖复杂场景，包括使用「第三方」认证——即「使用 Facebook / Google / X(Twitter) / GitHub 登录」背后的机制。

- **OAuth 1**：与 OAuth2 完全不同且更复杂（直接规定如何加密通信），如今已不流行。
- OAuth2 **不规定如何加密通信**，它期望应用使用 **HTTPS**。部署章节会介绍用 Traefik + Let's Encrypt 免费配置 HTTPS。

### 3. OpenID Connect 与 OpenID

| 概念 | 说明 |
|---|---|
| **OpenID Connect** | 基于 OAuth2 的扩展规范，明确 OAuth2 中模糊之处以提升互操作性。Google 登录使用它（底层是 OAuth2） |
| **OpenID（非 Connect）** | 试图解决同类问题但**不基于 OAuth2**，是独立的附加系统，如今已不流行 |

注意：Facebook 登录不支持 OpenID Connect，而是自己的 OAuth2 风格。

### 4. OpenAPI 与安全方案

**OpenAPI**（旧称 Swagger，现属 Linux Foundation）是构建 API 的开放规范，FastAPI 正是基于它——这正是自动交互文档、代码生成等能力的前提。OpenAPI 定义了多种安全方案（scheme）：

| 方案 | 说明 |
|---|---|
| `apiKey` | 应用特定密钥，可来自查询参数、请求头、cookie |
| `http` | 标准 HTTP 认证：`bearer`（`Authorization: Bearer <token>`，源自 OAuth2）、Basic、Digest 等 |
| `oauth2` | OAuth2 的各种「流程」（flow）：`implicit`、`clientCredentials`、`authorizationCode`（适合构建认证服务）；以及 `password`（适合在**同一应用内**直接处理认证，后续章节示例） |
| `openIdConnect` | 定义如何自动发现 OAuth2 认证数据（OpenID Connect 规范中的机制） |

集成 Google/GitHub 等第三方认证提供者是可能的且较容易；最复杂的是自己**创建**这样的认证服务，而 FastAPI 提供了工具帮你完成重活。

### 5. FastAPI 的安全工具

`fastapi.security` 模块为每种安全方案提供了相应工具，简化使用并**自动集成到交互式文档**。后续章节将看到它们如何为 API 增加安全性并自动反映在 `/docs` 中。

### 6. 易错点

- ✅ OAuth2 只是规范，不负责传输加密——必须自己上 HTTPS。
- ✅ OpenID Connect 基于 OAuth2；OpenID（非 Connect）是另一套已过时体系。
- ✅ `password` 流程适合自家应用内认证；`authorizationCode` 等适合做认证提供者。
- ✅ 若只想要用户名密码认证，可跳过术语直接看「安全 - 第一步」。

## 二、NestJS 对比

| 维度 | FastAPI（Python） | NestJS（TypeScript） |
|---|---|---|
| 安全工具来源 | `fastapi.security` 内置（`OAuth2PasswordBearer`、`HTTPBasic` 等） | 需装 `@nestjs/passport` + `passport-*` 策略，或 `@nestjs/jwt` |
| 规范落地 | 安全方案自动写入 OpenAPI，`/docs` 现成可用 | 靠 `@nestjs/swagger` 的 `ApiBearerAuth()` 等手动标注 |
| 认证抽象 | 安全工具本身是「可调用依赖」，直接 `Depends` | Passport Strategy + Guard（如 `AuthGuard('jwt')`） |
| 方案覆盖 | 直接支持 apiKey / http bearer / basic / oauth2 / openIdConnect | 支持广泛，但需按策略逐个安装与配置 |
| 第三方登录 | 可用通用 OAuth2 工具自行接入 | Passport 生态有大量现成策略（Google/GitHub 等） |
| 加密要求 | 依赖外部 HTTPS（文档明确说明） | 同样依赖 TLS/HTTPS，框架不内建加密通信 |

**核心差异一句话**：FastAPI 把安全方案做成内置的、可当依赖用的 `fastapi.security` 工具，并自动映射进 OpenAPI 文档；NestJS 通过 Passport 策略与 Guard 体系实现认证，生态广但要额外安装配置，文档标注需手动补。

## 三、针对性练习题

### 题 1（基础）
OAuth2 是否负责加密通信？FastAPI 文档对此给出的要求是什么？

<details>
<summary>参考答案</summary>

不负责。OAuth2 没有指定如何加密通信，它期望应用使用 HTTPS 进行通信。文档建议在部署章节中用 Traefik 与 Let's Encrypt 免费配置 HTTPS。
</details>

### 题 2（理解）
OpenID Connect、OpenID（非 Connect）、OAuth2 三者是什么关系？

<details>
<summary>参考答案</summary>

OpenID Connect 是**基于 OAuth2** 的规范，扩展并澄清了 OAuth2 中模糊之处以提升互操作性（如 Google 登录）。OpenID（非 Connect）试图解决同类问题但**不基于 OAuth2**，是独立附加系统，如今已不流行。OAuth2 本身是认证/授权规范。
</details>

### 题 3（辨析 / 代码）
OpenAPI 定义了哪些安全方案？`password` 流程适合什么场景？

<details>
<summary>参考答案</summary>

OpenAPI 安全方案：`apiKey`（查询/头/cookie）、`http`（bearer、Basic、Digest 等）、`oauth2`（implicit、clientCredentials、authorizationCode、password 等 flow）、`openIdConnect`（自动发现认证数据）。其中 `password` 流程适合**直接在同一个应用内**处理用户认证（本教程后续示例）；implicit/clientCredentials/authorizationCode 更适合构建独立的 OAuth2 认证提供者（如 Google/GitHub）。
</details>

### 题 4（进阶 · NestJS 迁移视角）
NestJS 通常用 `@nestjs/passport` 做认证。请说明 FastAPI 的实现思路有何不同。

<details>
<summary>参考答案</summary>

FastAPI 在 `fastapi.security` 中内置了对应各安全方案的工具（如 `OAuth2PasswordBearer`），它们本身就是「可调用依赖」，可直接用 `Depends` 注入，并自动写入 OpenAPI 让 `/docs` 出现 Authorize 按钮。NestJS 需安装 Passport 策略、定义 Strategy 类，再用 `AuthGuard('strategy')` 保护路由，文档标注需 `@nestjs/swagger` 手动补充。
</details>

### 题 5（思考）
为什么说 FastAPI 让安全处理「无需研究所有安全规范」就能上手？

<details>
<summary>参考答案</summary>

因为 FastAPI 基于 OpenAPI 标准，把常见安全方案封装成现成工具，且其继承体系（`SecurityBase` 等）让这些工具自动参与 OpenAPI 模式生成和交互文档。开发者只需选一个工具、用几行声明，就能获得规范的安全方案定义和文档集成，把精力留给业务逻辑而非规范细节。
</details>
