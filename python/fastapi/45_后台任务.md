## 一、章节笔记

### 1. 本章要解决什么问题

定义**在响应发出之后**才运行的任务。适用于"客户端不必等结果"的操作：

- 发送邮件通知：连接邮件服务器并发信往往要几秒，先返回响应，后台再发。
- 数据处理：收到需慢处理的文件时，先返回 `202 Accepted`，后台再处理。

### 2. 三步用法：声明参数 → 写任务函数 → `add_task`

```python
from fastapi import BackgroundTasks, FastAPI

app = FastAPI()

def write_notification(email: str, message=""):
    with open("log.txt", mode="w") as email_file:
        content = f"notification for {email}: {message}"
        email_file.write(content)

@app.post("/send-notification/{email}")
async def send_notification(email: str, background_tasks: BackgroundTasks):
    background_tasks.add_task(write_notification, email, message="some notification")
    return {"message": "Notification sent in the background"}
```

| 步骤 | 说明 |
|---|---|
| ① 声明参数 | 在路径操作函数中声明 `background_tasks: BackgroundTasks`，FastAPI 自动创建并注入该对象 |
| ② 写任务函数 | 普通函数即可，可接收参数；`async def` 或 `def` 都行，FastAPI 知道如何处理；本例写文件无阻塞 I/O，用普通 `def` |
| ③ `.add_task()` | 传入：任务函数 → 按顺序的位置参数 → 关键字参数 |

任务在**响应发送之后**执行，因此客户端无需等待。

### 3. 与依赖注入结合

`BackgroundTasks` 类型的参数可在多个层级声明：路径操作函数、依赖、子依赖等。FastAPI 会**复用同一个对象**，把所有后台任务合并后统一在后台运行：

```python
from typing import Annotated
from fastapi import BackgroundTasks, Depends, FastAPI

app = FastAPI()

def write_log(message: str):
    with open("log.txt", mode="a") as log:
        log.write(message)

def get_query(background_tasks: BackgroundTasks, q: str | None = None):
    if q:
        message = f"found query: {q}\n"
        background_tasks.add_task(write_log, message)
    return q

@app.post("/send-notification/{email}")
async def send_notification(
    email: str,
    background_tasks: BackgroundTasks,
    q: Annotated[str, Depends(get_query)],
):
    message = f"message to {email}\n"
    background_tasks.add_task(write_log, message)
    return {"message": "Message sent"}
```

效果：响应发出后写入 `log.txt`，若带查询参数则先写一条 query 日志，再写一条路径操作产生的 email 日志——两处 `add_task` 都作用于同一个 `BackgroundTasks` 对象。

### 4. 技术细节

- `BackgroundTasks` 直接来自 `starlette.background`，FastAPI 重新导出方便导入。
- 注意区分 **`BackgroundTasks`（复数）** 与 `BackgroundTask`（单数）：前者能作为路径操作参数由 FastAPI 注入，类似 `Request` 对象；后者需自己创建对象并作为 Starlette `Response` 返回。
- 任务执行时机在响应之后，因此不能修改已经发出的响应。

### 5. 何时不该用 BackgroundTasks

| 场景 | 建议 |
|---|---|
| 轻量、同进程任务（发邮件、写日志） | ✅ 用 `BackgroundTasks` |
| 需要访问同一应用的变量/对象 | ✅ 用 `BackgroundTasks` |
| 繁重计算、需跨进程/跨服务器 | ❌ 用 Celery 等，配 RabbitMQ/Redis 消息队列 |

Celery 类工具配置更复杂，但支持多进程、多服务器的后台任务。

### 6. 易错点

| 易错点 | 正确做法 |
|---|---|
| 导入 `BackgroundTask`（单数）当参数 | 用 `BackgroundTasks`（复数），单数不能由框架注入 |
| 在任务函数里改响应内容 | 任务在响应之后运行，改不了已发响应 |
| 把 heavy CPU 任务塞进来 | 会阻塞进程；用 Celery 等队列 |
| 以为任务在返回前执行 | `add_task` 只是登记，响应发出后才真正运行 |
| 依赖里另建一个 BackgroundTasks | 不要新建，声明参数即可，FastAPI 复用同一对象 |

## 二、NestJS 对比

| 维度 | FastAPI（Python） | NestJS（TypeScript） |
|---|---|---|
| 内置抽象 | `BackgroundTasks` 参数 + `.add_task()`，响应后执行 | 无同等的请求级内置抽象，需 `@nestjs/bull` / BullMQ 等队列模块 |
| 获取方式 | 路径操作/依赖中声明 `background_tasks: BackgroundTasks` 由框架注入 | 注入队列服务（如 `@InjectQueue('emails')`）并 `queue.add()` |
| 任务合并 | 路径操作与依赖共享**同一个** BackgroundTasks 对象，任务自动合并 | 每次 `queue.add()` 独立入队，无"合并"语义 |
| 执行模型 | 同一进程内，响应发送后由 Starlette 执行 | 独立 worker 进程消费队列（BullMQ 基于 Redis） |
| 可靠性 | 进程内，进程重启任务丢失 | 队列持久化，可重试、可跨机扩展 |
| 轻量任务成本 | 极低，零额外基础设施 | 需 Redis 和 worker 配置 |
| 与 DI 集成 | 依赖中也能 `add_task`，复用同一对象 | Provider 中注入队列服务，靠 Module 管理 |

**核心差异一句话**：FastAPI 的 `BackgroundTasks` 是"请求级、同进程、零配置"的轻量方案，适合发邮件这类小任务且能在依赖里共享同一个任务队列；NestJS 通过 BullMQ 等把任务丢到独立队列和 worker，配置更重但换来持久化、重试和横向扩展能力。

## 三、针对性练习题

### 题 1（基础）
`BackgroundTasks` 适合什么场景？任务何时执行？

<details>
<summary>参考答案</summary>

适合客户端无需等待结果的轻量操作：发送邮件通知、记录日志、慢处理后返回 `202`。任务在**响应发送之后**才执行，因此不能修改已发出的响应；客户端不必等待任务完成即可拿到响应。
</details>

### 题 2（理解）
写出一个接口 `POST /send-notification/{email}`，用 `BackgroundTasks` 把写日志的任务放到后台，并说明 `.add_task()` 三个参数的含义。

<details>
<summary>参考答案</summary>

```python
from fastapi import BackgroundTasks, FastAPI

app = FastAPI()

def write_notification(email: str, message=""):
    with open("log.txt", mode="w") as f:
        f.write(f"notification for {email}: {message}")

@app.post("/send-notification/{email}")
async def send_notification(email: str, background_tasks: BackgroundTasks):
    background_tasks.add_task(write_notification, email, message="some notification")
    return {"message": "Notification sent in the background"}
```

`.add_task()` 参数依次为：① 任务函数 `write_notification`；② 按顺序传给任务函数的位置参数 `email`；③ 关键字参数 `message="some notification"`。
</details>

### 题 3（辨析/代码）
`BackgroundTask` 与 `BackgroundTasks` 有什么区别？为什么作路径操作参数必须用后者？

<details>
<summary>参考答案</summary>

`BackgroundTasks`（复数）来自 `starlette.background`，FastAPI 重新导出，能作为路径操作/依赖的参数由框架自动创建并注入，类似 `Request`。`BackgroundTask`（单数）是单个任务对象，不能由框架注入，必须自己创建并包装进 Starlette `Response` 返回。所以想用"声明参数 + add_task"的写法必须用复数形式。
</details>

### 题 4（进阶 · NestJS 迁移视角）
你在 NestJS 里习惯用 `@InjectQueue()` 把任务发到 BullMQ。请写出功能等价的 FastAPI 示例：路径操作和依赖各添加一个日志任务，响应后一起写入 `log.txt`，并说明 FastAPI 如何将两者合并。

<details>
<summary>参考答案</summary>

```python
from typing import Annotated
from fastapi import BackgroundTasks, Depends, FastAPI

app = FastAPI()

def write_log(message: str):
    with open("log.txt", mode="a") as log:
        log.write(message)

def get_query(background_tasks: BackgroundTasks, q: str | None = None):
    if q:
        background_tasks.add_task(write_log, f"found query: {q}\n")
    return q

@app.post("/send-notification/{email}")
async def send_notification(
    email: str,
    background_tasks: BackgroundTasks,
    q: Annotated[str, Depends(get_query)],
):
    background_tasks.add_task(write_log, f"message to {email}\n")
    return {"message": "Message sent"}
```

FastAPI 在整条依赖链中复用**同一个** `BackgroundTasks` 实例，两处 `add_task` 都登记到它上面，响应发出后按登记顺序统一执行。NestJS 的 BullMQ 每次 `queue.add()` 是独立入队，不具备这种自动合并语义。
</details>

### 题 5（思考）
什么情况下应放弃 `BackgroundTasks` 改用 Celery？为什么？

<details>
<summary>参考答案</summary>

当任务计算繁重、耗时长，或需要在其他进程/服务器运行、需要持久化和重试、需要与主进程隔离时。因为 `BackgroundTasks` 在当前进程内执行，会占用应用进程资源，进程重启任务即丢失，且无法跨机扩展。Celery 配 RabbitMQ/Redis 把任务放入消息队列由独立 worker 消费，配置更复杂但支持多进程、多服务器与可靠投递。
</details>
