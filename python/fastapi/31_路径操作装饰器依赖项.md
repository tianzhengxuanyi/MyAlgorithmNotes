# 31 · 路径操作装饰器依赖项（Dependencies in Path Operation Decorators）

> 官方文档：<https://fastapi.tiangolo.com/zh/tutorial/dependencies/dependencies-in-path-operation-decorators/>

## 一、章节笔记

### 1. 适用场景

有时我们**不需要依赖的返回值**，或依赖本身不返回值，但仍需执行/解析它。这时不必在路径操作函数的参数里用 `Depends`，而可在**路径操作装饰器**上添加由 `Depends()` 组成的 `list`，通过 `dependencies` 参数声明。

```python
from typing import Annotated

from fastapi import Depends, FastAPI, Header, HTTPException

app = FastAPI()

async def verify_token(x_token: Annotated[str, Header()]):
    if x_token != "fake-super-secret-token":
        raise HTTPException(status_code=400, detail="X-Token header invalid")

async def verify_key(x_key: Annotated[str, Header()]):
    if x_key != "fake-super-secret-key":
        raise HTTPException(status_code=400, detail="X-Key header invalid")
    return x_key

@app.get("/items/", dependencies=[Depends(verify_token), Depends(verify_key)])
async def read_items():
    return [{"item": "Foo"}, {"item": "Bar"}]
```

### 2. 执行与返回值规则

| 规则 | 说明 |
|---|---|
| 声明位置 | 装饰器上：`@app.get("/items/", dependencies=[...])` |
| 值的类型 | 由 `Depends()` 组成的 `list` |
| 执行方式 | 与普通依赖一样执行/解析 |
| 返回值 | **即使依赖返回值，也不会传给路径操作函数** |
| 异常 | 可像普通依赖一样 `raise`（如 `HTTPException`），阻断请求 |
| 需求项 | 可声明请求需求（Header 等）或其他子依赖 |

### 3. 为什么用它

- 避免声明「永远用不到」的函数参数，防止编辑器/静态工具报「未使用参数」错误。
- 避免新人误以为代码里有无用的未使用参数。
- 可复用那些「在别处会用到返回值」的普通依赖——即使此处不用其返回值，它仍会执行。

> 注意：示例用自定义头 `X-Key` / `X-Token` 演示。实际开发（尤其安全场景）应使用 FastAPI 内置安全工具（后续章节）。

### 4. 为一组路径操作定义依赖项

本章只针对单个路径操作。若要为**一组**路径操作声明同一个 `dependencies` 参数，需使用 `APIRouter`（在「大型应用 - 多文件」章节介绍）。更进一步，还有作用于整个应用的**全局依赖项**（下一章）。

### 5. 易错点

- ✅ `dependencies` 是装饰器的参数，值是 `Depends(...)` 的列表，不是函数参数注解。
- ✅ 这里依赖的返回值会被丢弃，需要返回值时应改用函数参数注入。
- ✅ 依赖项抛出的异常照样生效，可用于鉴权拦截。
- ✅ 依赖仍可有自己的子依赖与请求需求。

## 二、NestJS 对比

| 维度 | FastAPI（Python） | NestJS（TypeScript） |
|---|---|---|
| 装饰器级依赖 | `@app.get(..., dependencies=[Depends(fn)])` | 无内置等价；用 Guard / Middleware / Interceptor 挂载 |
| 关注点 | 执行副作用（校验、鉴权），丢弃返回值 | Guard 做鉴权（返回 boolean）、Middleware 做请求预处理 |
| 未使用参数问题 | 用装饰器依赖避免声明无用参数 | 用 `@UseGuards()` / `@UseInterceptors()`，不进 handler 签名 |
| 返回值处理 | 即使有返回值也不传给 handler | Guard 的 `canActivate` 返回布尔决定放行；Interceptor 可变换响应 |
| 异常拦截 | 依赖里 `raise HTTPException` | Guard / Pipe 里 `throw HttpException` |
| 分组作用域 | 单路由靠装饰器参数；分组靠 `APIRouter` | `@UseGuards()` 可作用于方法、控制器类或全局 |
| 请求数据需求 | 依赖参数可用 `Header()` 等自动提取 | Guard 可通过 `ExecutionContext.switchToHttp().getRequest()` 取请求 |

**核心差异一句话**：FastAPI 用装饰器上的 `dependencies` 列表挂载「只执行、不取返回值」的依赖，简单直接；NestJS 没有对应语法，同类横切逻辑需拆成 Guard（鉴权判定）、Middleware（预处理）或 Interceptor（响应变换）并通过 `@UseGuards()` 等显式装配。

## 三、针对性练习题

### 题 1（基础）
用装饰器 `dependencies` 的方式，为 `GET /admin/` 添加一个校验头 `X-Role`（值必须为 `admin`）的依赖，不满足则抛 403，handler 本身不接收任何参数。

<details>
<summary>参考答案</summary>

```python
from typing import Annotated
from fastapi import Depends, FastAPI, Header, HTTPException

app = FastAPI()

async def verify_admin(x_role: Annotated[str, Header()]):
    if x_role != "admin":
        raise HTTPException(status_code=403, detail="Forbidden")

@app.get("/admin/", dependencies=[Depends(verify_admin)])
async def admin_panel():
    return {"secret": "data"}
```

`verify_admin` 会被执行并校验头，但其返回值（这里无 return）不会传给 `admin_panel`。
</details>

### 题 2（理解）
什么时候应该用装饰器的 `dependencies`，而不是在函数参数里用 `Depends`？

<details>
<summary>参考答案</summary>

当依赖的返回值不需要在路径操作函数里使用、甚至依赖没有返回值，但仍需执行它（如鉴权、头校验、日志）时，用装饰器 `dependencies`。好处是避免在 handler 签名里出现「未使用参数」，防止编辑器/工具报错，也避免误导他人。若需要返回值参与业务逻辑，则在函数参数中用 `Depends` 注入。
</details>

### 题 3（辨析 / 代码）
下面依赖 `verify_key` 返回了 `x_key`，`read_items` 里能拿到这个值吗？

```python
async def verify_key(x_key: str = Header()):
    if x_key != "k": raise HTTPException(400, "bad key")
    return x_key

@app.get("/items/", dependencies=[Depends(verify_key)])
async def read_items():
    return {"x_key": ???}
```

<details>
<summary>参考答案</summary>

拿不到。装饰器 `dependencies` 中的依赖即使有返回值，也**不会传给路径操作函数**——它只被执行/解析。若要在 handler 中使用 `x_key`，必须改为函数参数注入：`async def read_items(x_key: str = Depends(verify_key))`。
</details>

### 题 4（进阶 · NestJS 迁移视角）
你在 NestJS 中用 `@UseGuards(AuthGuard)` 保护一个 handler，Guard 只判断放行与否、handler 不需要其返回值。请用 FastAPI 的装饰器依赖写出等价实现。

<details>
<summary>参考答案</summary>

```python
from typing import Annotated
from fastapi import Depends, FastAPI, Header, HTTPException

app = FastAPI()

async def auth_guard(x_token: Annotated[str, Header()]):
    if x_token != "valid-token":
        raise HTTPException(status_code=401, detail="Unauthorized")

@app.get("/protected/", dependencies=[Depends(auth_guard)])
async def protected():
    return {"ok": True}
```

两者都在 handler 之外做拦截；差异是 FastAPI 复用「依赖」这一个统一概念（可含任意参数与子依赖），NestJS 则拆出 Guard 这一专门抽象，需 `@UseGuards()` 装配且通过 `ExecutionContext` 取请求数据。
</details>

### 题 5（思考）
本章示例用了自定义头 `X-Token`，文档为何提醒实际安全场景应使用 FastAPI 内置安全工具？

<details>
<summary>参考答案</summary>

自定义头只是演示依赖机制，手写鉴权容易遗漏细节（如 token 解析、错误处理、与 OpenAPI 安全方案集成）。FastAPI 内置安全工具（如 `OAuth2PasswordBearer`、`HTTPBasic`、`Security` 等）能自动生成 OpenAPI 安全方案、在 `/docs` 中提供授权交互，并与依赖系统无缝衔接，更规范、安全且文档友好。
</details>
